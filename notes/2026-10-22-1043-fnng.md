# The agentic loop

Claude by itself will answer one request with one response

To take action it needs TOOLS it can access, like reaching into a toolbox

Claude using tools and working in a loop to get things done = 'an agent'

`STOP_REASON` is what actually stops the loop, otherwise it just keeps going

Everything in Domain 1 lessons build on this loop



**CASE STUDY EXAMPLE:**

A mechanic makes an agent that answers customer messages

The agent must look up the order and check the diary before it replies

An agent with a broken loop stops halfway through the task when it can't load the right tools



**THE AGENTIC LOOP**

Sends a request to Claude via the <span data-infra>|Messages api.</span> Includes a record of everything discussed and all prompts, and any previous toolcalls.

Then Claude will consult `stop_reason` again. Two things can happen now - call another tool, or end turn like in Civ 5.

If it is tool use it will call another tool, if its end turn it will just wrap up.

When the tool use part breaks, the model has nothing new to reason about, and if it's not stopped with an end turn, it will just keep looping ad infinitum. See: broken OpenClaw agents.



**KEY CONCEPT**

`stop_reason` is the only reliable way to control a loop. 



**MODEL DRIVEN DECISION MAKING**

Claude decides which tool to call from the current context

- reads the task
- looks at which tools are available
- picks the best one

This is how it works automatically. But we can force claude to use certain tools via a pre-configured decision tree or <span data-workflow>fixed tool sequence</span>.

The advantage of a model-driven approach is flexibility. Claude can bend to the needs of the task by calling the tools best suited to delivering it.

But some things need compliance like financial operations. In these cases we hard code to avoid problems. We call this <span data-workflow>programmatic enforcement</span>.



**ANTI PATTERNS**

An anti pattern is a solution that seems good on the face of it, but turns out to be rubbish

ANTI PATTERN 1 - relying on natural language signals

Sometimes Claude can say ambiguous things that sound complete, but actually aren't

ANTI PATTERN 2 - capping by number of loops run

Can either lead to it being cut off before something is complete, or it runs useless loops

ANTI PATTERN 3 - checking the agent's own logs to see if it finished

Claude can come out with all kinds of different silly text whilst it is working  

**EXAM PREP**

Get the lifecycle right and most of Domain 1 will fall into place:

- start on `tool_use` 
- terminate on `end_turn`
- reject all of the anti-patterns

The exam prefers model-driven decision making because it flexes.
